# Virtual Café

> Your favourite café, always within reach.

An implementation of **Virtual_Cafe_SPEC_v1.0.md** — a 2.5D isometric café you
can work in. Pick a seat, listen to the room, and when your team arrives, sit at
the same table and talk. No meeting link, no camera, no account.

This repository covers the P0 scope from Appendix B of the spec, plus the two
P1 features that the core loop depends on (Focus Mode and table chat).

```
┌──────────────┐   HTTP (guest session, join, voice token, moderation)
│   Next.js    │◀─────────────────────────────────────────────────┐
│   web client │   WebSocket (presence, movement, seats, voice)    │
│              │◀──────────────────────────────────────────┐      │
│  canvas 2.5D │                                           ▼      ▼
│  Web Audio   │                                    ┌──────────────────┐
│  LiveKit SDK │                                    │   NestJS server  │
└──────────────┘                                    │  InstanceManager │
                                                    │  Socket.IO       │
                                                    │  Store (PG/mem)  │
                                                    └──────────────────┘
```

## Running it

```bash
npm install
npm run dev
```

- Web: <http://localhost:3000>
- API: <http://localhost:4000>

Nothing else is required. With no `DATABASE_URL` the server keeps durable data
in memory, and with no `LIVEKIT_*` keys the café runs with voice reported as
unavailable — you can still walk, sit, set a status, chat at your table and
listen to the room. Copy `.env.example` to `.env` to change any of it.

The server reads the repo-root `.env` on boot and logs which file it used.
Variables already set in your shell always win over the file.

### Enabling voice (LiveKit)

Voice needs an SFU. The client and the token minting are already built — all
that is missing is credentials.

1. Create a free project at <https://cloud.livekit.io>.
2. Open **Settings → Keys** and create a key. Copy three values: the project
   URL (starts with `wss://`), the API key (starts with `API`) and the secret,
   which is shown only once.
3. Put them in `.env` at the repo root:

   ```bash
   LIVEKIT_URL=wss://your-project.livekit.cloud
   LIVEKIT_API_KEY=APIxxxxxxxxxxxx
   LIVEKIT_API_SECRET=your-secret
   ```

4. Restart the server. The `No SFU configured` warning should be gone.

The key and secret never leave the server. The browser receives only a
short-lived JWT scoped to one table's room — see [Voice privacy](#voice-privacy).

### Ngôn ngữ và SEO (tiếng Việt)

The interface and all user-facing server messages are in Vietnamese, and the
landing page is the only indexable route. Everything brand-related lives in
`apps/web/src/lib/site.ts` — change `SITE_NAME` there to rename the product in
the title tag, the H1, the social card and the structured data at once.

Set the production domain **at build time**; the landing page is statically
prerendered, so metadata is baked in by `next build` and exporting the variable
only before `next start` leaves canonical URLs on the fallback:

```bash
SITE_URL=https://your-domain.vn npm run build
```

What that produces: `<html lang="vi">`, Vietnamese title and meta description,
canonical URL, Open Graph and Twitter cards with `og:locale=vi_VN`,
schema.org `WebApplication` JSON-LD, `/robots.txt` and `/sitemap.xml`, and a
1200×630 social card generated by `app/opengraph-image.tsx`. The `/cafe` route
is `noindex` and disallowed in robots.txt — it is a canvas behind a guest
session with nothing for a crawler to read.

### Scaling with occupancy

Movement is broadcast on a fixed server tick (`WORLD_TICK_HZ`, 15 Hz), not once
per inbound message. A per-event relay costs N×(N−1)×`MOVE_SEND_HZ` frames per
second, so the work grows quadratically with the number of people in a room.
Batching makes the frame count linear while carrying the same information.

Measured with `node tools/load-test.mjs <guests>`:

| Guests | Frames/s before | Frames/s after | Reduction |
| --- | --- | --- | --- |
| 10 | 1,192 | 134 | 8.9× |
| 25 | 8,100 | 335 | 24× |
| 50 | 32,551 | 665 | 49× |

Move latency stayed at p50 0 ms throughout: the authority logic was never the
bottleneck, the socket fan-out was.

Two things to know before raising `INSTANCE_CAPACITY` above 25:

- There are **31 user seats**, so a full instance already has only 6 spare
  chairs. Above 31, people would be admitted with nowhere to sit.
- A table *is* the voice group, so a team of four needs an empty four-seat
  table, not four free chairs. Only three tables seat four or more and only one
  seats five or six, so group seating runs out well before chairs do.

### Demo build

```bash
NEXT_PUBLIC_DEMO_MODE=1 SITE_URL=https://your-domain.vn npm run build
```

Demo mode hides the per-person moderation menu (mute / block / report) in the
People panel, so the screen is quieter while presenting and nothing opens on a
stray click. It is a flag rather than a deletion: SPEC 9 lists those as user
capabilities, and the server keeps the endpoints and the `moderation_reports`
and `user_blocks` tables in both builds. Leave the variable unset for the full
product.

Ambient characters keep their `· NPC` label in every build — SPEC 8.1 requires
a visible marker and forbids presenting them as real users.

## Deploying

Two pieces, two hosts: the Next.js client on Vercel, the realtime server on
Render with a Postgres database.

> **The API runs as exactly one instance.** Presence, seat ownership and
> voice-group membership live in the server process's memory and there is no
> Socket.IO Redis adapter. A second instance is a second, invisible café:
> people who believe they are in the same room cannot see each other and seat
> authority splits. `render.yaml` pins `numInstances: 1`. Add
> `@socket.io/redis-adapter` and move presence into Redis before raising it.

Order matters, because each side needs the other's URL:

**1. API on Render.** New → Blueprint, point it at this repo; `render.yaml`
creates the web service and the database. Set the three secrets it asks for
(`LIVEKIT_URL`, `LIVEKIT_API_KEY`, `LIVEKIT_API_SECRET`) from
cloud.livekit.io → Settings → Keys. `SESSION_SECRET` is generated by Render
and `DATABASE_URL` is wired automatically. Note the URL it gives you, e.g.
`https://gocquen-api.onrender.com`.

The database schema is applied on every boot and every statement is
`IF NOT EXISTS`, so there is no migration step to run.

**2. Web on Vercel.** New Project → this repo → **Root Directory `apps/web`**.
Vercel detects the npm workspaces at the repo root and installs from there, so
no install command needs overriding; `apps/web/vercel.json` only points the
build at `vercel-build`, which compiles the shared package first.
Add two environment variables, then deploy:

```bash
NEXT_PUBLIC_SERVER_URL=https://gocquen-api.onrender.com
SITE_URL=https://gocquen.vercel.app
```

Both are read at **build** time, so changing either needs a redeploy. Add
`NEXT_PUBLIC_DEMO_MODE=1` if you want the demo build.

The root layout mounts Vercel Web Analytics (`<Analytics />` from
`@vercel/analytics/next`). It is cookieless and records page views and
routes, never an identifier that follows anyone between sites — the only kind
of measurement this café carries. The component reports nothing outside a
Vercel deployment, so local runs and the Render API are unaffected, but the
data only appears once **Web Analytics is switched on for the project** in
the Vercel dashboard (Project → Analytics → Enable). The code alone does not
turn it on.

**3. Close the loop.** Back on Render, set `CORS_ORIGINS` to the Vercel URL
(comma separated, no trailing slash) and redeploy. In production the allow-list
is used verbatim — anything not listed is refused, including localhost.

### Notes

- **Free Render services sleep when idle**, so the first visitor after a quiet
  spell waits for a cold start. Check Render's current free-tier terms; a paid
  instance stays awake.
- **`DATABASE_SSL`** is left unset because Render hands over an internal
  connection string that never leaves its private network. Pointing the server
  at an external database (Neon, Supabase, RDS) needs `DATABASE_SSL=require`,
  which encrypts without verifying the certificate — the usual setting for
  managed providers. `strict` verifies against the system CA store.
- **Never commit `.env`.** It is gitignored; `.env.example` is the template.

## Chia sẻ màn hình theo bàn

Someone sitting at a table can share their screen with the people at that
same table. It is a collaboration feature, not a meeting: there is no
café-wide broadcast and no way to watch a table you are not sitting at.

- One publisher per table. The slot is taken synchronously, so two people
  pressing the button together cannot both win it.
- Viewing requires only that you are **seated** at the table. Joining the
  voice conversation is a separate, deliberate act.
- The share ends by itself when the publisher stops, stands up, changes
  table, leaves, disconnects, or ends capture with the browser's own button.
- Metadata only is persisted — who shared, at which table, for how long.
  **No screen content is ever stored or recorded.**

### While a screen is live, it is the room

A live screen takes the interface over by itself — for whoever is sharing and
for everyone who joins to watch. The shared screen fills the window, the side
panels stand down, and the café goes behind it until the share ends. Nobody
has to find an expand button to read what is being shown.

**Quay lại quán** collapses it back to the floating panel, and that decision
is remembered for as long as that share lasts: the layout will not expand over
someone again after they have asked for the café back. The next share at the
table is judged afresh. Ending the share — or standing up — hands the café
back on its own.

(This is unrelated to **Focus Mode** in the audio dock, which dims the room's
ambience. The names collide; the features do not touch.)

The rule is one pure function, `nextScreenShareFocus`, applied from `useCafe`
rather than from the panel — a share going live has to take the interface over
even when the side panels are closed and the panel is not mounted to notice.

### How a table's screen is kept private

Four independent layers, none of which is the UI:

1. **Derivation** — the table comes from the seat the *server* says you
   occupy. No endpoint, body or socket payload accepts a table id, so there
   is no parameter to tamper with.
2. **A separate room per table** — media travels through
   `cafe__<instance>__<group>__screen`, named by the server. A token grants
   exactly one room, so another table's stream is unreachable rather than
   merely hidden.
3. **A room apart from voice** — the screen room is deliberately *not* the
   voice room. A voice token carries the right to hear everyone at the table,
   and watching a screen must not quietly grant that, so a screen token
   carries no microphone at all.
4. **Publish scoping** — `screen_share` appears in a token only for whoever
   holds the slot. A viewer who modifies their client still cannot publish.

The smoke suite proves this against a running server: `npm run smoke` seats
two guests at different tables and checks that the second is not told a
session exists, cannot stop it, never receives the start event, and receives
a token naming a different room entirely.

`npm run screen-share` goes a step further and proves the whole path, SFU
included: three guests walk to real seats, one starts a share over the same
REST endpoint the web app uses, and the check is what the other two hear —
the one at that table is told, the one at the next table is told nothing.
It then opens a headless browser, publishes a stand-in capture with the
publisher's own token and subscribes with the viewer's, and asserts that live
frames arrive rather than a black rectangle. This is the leg no unit test can
reach, and it is where the bug below was caught.

**What this cannot do:** stop someone who is legitimately at your table from
screenshotting or recording what they see with other software. Share
accordingly.

### Two doors, one announcement

The publisher slot can be claimed over REST or over the socket, and for a
while only the socket door announced anything. The web app uses the REST
door, so a share was claimed that nobody was ever told about: the other
people at the table never learned to join the screen room, and the
publisher's own client — seeing no session — decided it did not need a
connection and tore its freshly published track straight back down. Pressing
**Chia sẻ màn hình** appeared to do nothing at all.

Both doors now announce through `ScreenShareService` itself rather than
either caller, so there is no longer a choice to get wrong. `npm run
screen-share` is the regression test.

### Trying it

Screen sharing needs the `LIVEKIT_*` credentials (see *Enabling voice*) — the
same SFU carries both. Then open the café in two browser windows, sit both at
the same table, and press **Chia sẻ màn hình** in one.

| Endpoint | What it does |
| --- | --- |
| `GET /voice/screen-share` | The session at your table, or none |
| `POST /voice/screen-share/start` | Take the table's slot |
| `POST /voice/screen-share/stop` | Release it |
| `POST /voice/screen-share/token` | A token for your table's screen room |

None of them takes a table id.

### `npm run dev` fails with `EADDRINUSE`

```
Error: listen EADDRINUSE: address already in use :::3000      (web)
Error: listen EADDRINUSE: address already in use 0.0.0.0:4000 (server)
```

A previous dev run is still alive and holding the port. On Windows each half of
`npm run dev` runs behind a `cmd.exe` shim, so closing the terminal — or a
Ctrl+C that does not propagate through the shim — can leave the underlying
`next` and `nest` processes running. Clear them and start again:

```bash
npm run dev:fresh        # or: npm run free-ports && npm run dev
```

Use `node tools/free-ports.mjs --dry-run` first if you want to see which
processes would be killed.

## Project layout

```
packages/shared/     Map data, seats, isometric maths, event schemas, constants
apps/server/         NestJS: HTTP API, Socket.IO gateway, instance authority
apps/web/            Next.js: landing page, canvas renderer, audio, UI panels
tools/               Smoke test, screen share and visual check harnesses
```

The shared package is the contract. The map, the seat table and the collision
grid are defined **once** and imported by both sides, so the client cannot
predict a position the server would reject for a different reason.

## How the important parts work

### Server authority

`InstanceManager` is the whole café in one class, and nothing outside it touches
the state maps. It owns:

- **Instance assignment** — the fullest instance that still has room, so people
  meet each other instead of being scattered one per room.
- **Movement validation** — distance against `(WALK_SPEED + tolerance) × elapsed`,
  then the shared collision grid. A rejected move comes back as a correction and
  the client snaps.
- **Seat claims** — Node is single threaded, so the check and the write in
  `sit()` cannot interleave. Two people racing for the last chair always produce
  exactly one winner and one `conflict`.
- **Voice scope** — see below.
- **Reconnect** — a dropped socket keeps the avatar and the seat for
  `DISCONNECT_GRACE_SECONDS`, then both are released and the ghost disappears.

### Voice privacy

This is the risk the spec rates highest, so it is enforced structurally rather
than by client behaviour:

1. You must be **sitting** before you can join a conversation.
2. The group you get is the `seatGroupId` of the seat the **server** says you
   occupy. Asking for a different group is rejected, not honoured.
3. The SFU room name is `cafe__<instanceId>__<groupId>`. There is no café-wide
   room to subscribe to by accident, and two instances never share a room.
4. The access token is short lived and only grants that one room.
5. Standing up, changing table, disconnecting or reconnecting all drop you out
   of the group. **The microphone never resumes by itself.**

The background chatter you hear is a synthesised ambient layer. No one's
microphone is ever replayed to the room (SPEC 6.2).

### Audio

Six layers — music, café room, weather, chatter, live voice, UI — each on its
own gain node, so muting one never touches another. Focus Mode dims the room
and the chatter for *you*; it does not change who can hear you.

Everything except live voice is **synthesised at runtime** with the Web Audio
API: generative chords and felt-piano notes, brown-noise room tone, espresso
hiss, grinder, cup clinks, chair scrapes, the door bell, keyboard patter and
rain on glass. That is a deliberate answer to SPEC 15.4 — generated audio is
original by construction, so the MVP ships with a complete soundscape and no
licensing ambiguity. To use licensed stems instead, replace the generators
behind the existing gain nodes in `apps/web/src/audio/engine.ts`; the mixing,
controls and persistence stay as they are.

### Rendering

A hand-written Canvas2D isometric renderer rather than a game engine, because
there are no sprite assets to load: every tile, chair, plant and avatar is drawn
from the same palette and camera angle, which rules out the mixed-source art
drift the spec warns about (SPEC 15.6).

Two details worth knowing:

- The floor and its decals are painted once into an offscreen canvas; only
  furniture, seats and avatars are re-sorted per frame.
- Long furniture is **sliced per tile** for depth sorting. A single painter's
  depth cannot be correct for a six-seat table with people on both sides, so
  each tile sorts independently; the slices overlap slightly and share a colour,
  which hides the seams.

## Testing

```bash
npm test                 # 22 unit tests, no server required
```

Covers the acceptance criteria that are pure logic: instance isolation, the seat
race, movement rejection, voice scoping, status restoration and reconnect
behaviour (SPEC 17.1, 17.3).

```bash
# terminal 1
npm run dev
# terminal 2
npm run smoke
```

16 end-to-end checks against a live server with two real socket clients: guest
entry, instance assignment, teleport rejection, the seat race, table-scoped
voice and chat, rate limiting, reconnect, malformed payloads and metrics.

```

Drives the real café in headless Chrome (Chrome or Edge, found automatically),
walks to a seat, sits down and captures the result. Set `WEB_URL` if the app is

```

occupancy, presence and the people panel without opening a dozen tabs. Ctrl+C
sends them home.

## Deployment notes

- `SESSION_SECRET` **must** be set in production; the server refuses to start
  with the development default.
- Terminate TLS in front of the server: the spec requires HTTPS/WSS in
  production, and the app sets only basic hardening headers itself.
- Set `CORS_ORIGINS` to your real origin. In development any `localhost` port is
  accepted so running on a spare port does not look like an outage.
- Set `DATABASE_URL` and run with `pg` installed to keep users, preferences,
  reports and blocks across restarts. The schema is applied on boot from
  `apps/server/src/storage/schema.sql`.

## Scope

**Implemented** — everything in Appendix B (P0), plus Focus Mode (FR-015) and
table chat (FR-016). See [docs/SPEC-COVERAGE.md](docs/SPEC-COVERAGE.md) for the
feature-by-feature mapping.

**Deliberately not implemented**, with reasons:

- **Multi-node realtime.** Instance state lives in one process, which is correct
  and race-free for a single realtime node. Running several nodes needs a shared
  registry for occupancy and seat locks; `InstanceManager` is the only seam that
  would change, and nothing outside it reads the state maps.
- **Ambient NPC animation.** The five NPCs are placed, labelled as scenery in
  both the world and the people list, and restricted to seats flagged `npcOnly`.
  They do not yet have per-activity animation cycles (FR-017 is P1).
- **P2 features** — avatar customisation, Pomodoro, the order counter and music
  requests (FR-018 to FR-021).
- **Load and soak testing** (SPEC 17.2). The 20–25 per instance target needs a
  real load run; `INSTANCE_CAPACITY` is a configurable guess until then, exactly
  as the spec asks.
